# Agent-Directed Demo Video

Act as the explorer and director. Demo Recorder makes no model API calls; use repository tools for reasoning and the deterministic CLI for execution.

Default to Demo Recorder's launched Playwright Chromium. Do not load or invoke Playwriter unless the user explicitly requests Playwriter. If the user requests their existing browser without naming a tool, use Playwright CDP for exploration only; rehearsal and recording still require launched Chromium. Do not switch to Playwriter automatically for login or setup issues.

Use the versioned, user-cached CLI described in [the first-run setup guide](references/setup.md) for every Demo Recorder command. Never use `npx` for the runtime, install it globally, or add it to the target project. In commands below, `node "$DR_CLI"` means the verified cached `@noice-tech/demo-recorder` entry point established by that guide.

Pass `--project DIR` (default `.`) to exploration, auth, rehearsal, recording, and rendering. For `inspect`, pass the video path explicitly. Keep artifacts in that folder: `session.json`, `observations/`, `plan.json`, `presentation.json`, `recording/`, and `output.mp4`. Files are the only API between stages.

1. Check Node before any npm command: `node -e 'const major=Number(process.versions.node.split(".")[0]); process.exit(major >= 22 ? 0 : 1)'`. If Node is absent or unsupported, stop and ask the user to install Node.js 22 or newer; never install a system Node runtime automatically.
2. Follow [the first-run setup guide](references/setup.md). Then run `node "$DR_CLI" doctor --json` and inspect every reported check.
3. If FFmpeg or ffprobe is missing or incompatible, direct the user to https://github.com/noice-tech/demo-recorder/blob/main/docs/install-ffmpeg.md and wait for them to install it; never run a system package manager for them. If Playwright Chromium is missing, explain its user-cache download and ask for separate explicit permission before running `node "$DR_CLI" setup --chromium --accept-downloads --json`. Rerun doctor after each repair and continue only when its final status is `ready`.
4. Turn the request into a concise goal, audience, duration, and safety constraints. Choose the capture viewport and output canvas before exploration: infer them from an explicit user request or platform, otherwise keep the 1440×900 browser and 16:9 canvas defaults. Browser viewport and output canvas are independent—a widescreen browser can be framed inside a square or portrait canvas. Direct the capture as a human performance: the cursor should travel to controls, clicks should cause route changes, and page arrivals should have time to register.
5. If source is available, inspect `package.json`, routes, navigation, tests, auth, and startup docs. Never read or print secret values.
6. Explore safely with a persistent session. Pass `--viewport WIDTHxHEIGHT` whenever the capture viewport is not the 1440×900 default so layout evidence matches rehearsal and recording:
   `node "$DR_CLI" explore start --project DIR --url URL [--viewport WxH] [--policy read-only|reversible] [--headed]`,
   then one bounded `node "$DR_CLI" explore act --project DIR --input action.json` at a time, and finish with `node "$DR_CLI" explore finish --project DIR`. The session protocol is in [the exploration guide](references/exploration.md). Only when the user requests their existing Chrome, first run `explore pages --driver cdp --target <cdp-url>`, then attach with `explore start --project DIR --driver cdp --target <cdp-url> --page <id>`. CDP is exploration-only; use launched Playwright Chromium for rehearsal and recording.
7. Read the returned observation, `observations/<id>.yml`, and `observations/<id>.png`. Each `act` already returns the next observation with fresh refs; use `node "$DR_CLI" explore observe --project DIR` only for pages that changed without an explorer action. Keep a directed exploration to one session and usually 6–10 bounded actions. Treat refs as observation-scoped. Every action reports whether its durable target uniquely resolves. Do not submit forms or use destructive controls during exploration.
8. If login is required in a launched browser, run `node "$DR_CLI" auth start --project DIR --url <login-url>` (add `--headed`), tell the user to complete login in the visible browser, then run `node "$DR_CLI" auth save --project DIR` and pass the saved file to `explore start --storage-state DIR/auth-state.json`. An attached browser can reuse login for exploration only. For authenticated rehearsal and recording, save login state in a launched browser and pass `--storage-state DIR/auth-state.json` to both commands.
9. Write `DIR/plan.json` using the durable `target` recipes gathered during exploration. Do not copy observation refs into a plan. Add an `expect` to any step whose result matters. Keep styling in a separate `DIR/presentation.json`; the plan is capture direction only. Preserve the exploration `viewport`. Apply the no-teleport rule: `navigate` may establish the initial page only; every later route change that belongs to the story must be a `click` on a visible, uniquely resolved link or button followed by an `expect` on the destination. Details are in [the planning guide](references/planning.md).
10. Run `node "$DR_CLI" plan rehearse --project DIR --json` (add `--storage-state DIR/auth-state.json` when authenticated). It validates the plan, runs it in a fresh browser, and checks every `expect`. Require `ok: true` and `captureReady: true` before capture. Before accepting it, audit the plan for human pacing: no mid-story `navigate`, no immediate interaction on page arrival, no robotic sequence of identical waits, and no unnecessary cursor travel. Use varied holds around roughly 600–1600ms, longer for important reveals. On failure, read `rehearsal-report.json` and `evidence/step-N.png|yml`, repair only the failing area, and rerun.
11. Run `node "$DR_CLI" record --project DIR` (with the same `--storage-state` when authenticated) and wait for capture and FFmpeg rendering. `record` requires a passing rehearsal of the current plan contents. Unchanged reruns reuse that approval; edits require rehearsal again. Do not use `--skip-rehearsal` unless the user explicitly accepts bypassing verification. The launched driver enables the runtime effect boundary for the run, so off-origin navigation, form submits, popups, and downloads are aborted and the recording records `guarded: true`. If a driver cannot provide the boundary, `record` requires `--allow-unguarded` and records `guarded: false`. It writes `DIR/recording/browser.mp4` + `DIR/recording/events.json` and then `DIR/output.mp4`. Never ship the raw `browser.mp4`.
12. Run `node "$DR_CLI" inspect DIR/output.mp4 --contact-sheet` and read the metadata and sheet for canvas aspect ratio, outer padding, browser framing, cursor, clicks, zooms, pacing, alignment, and the intended final state. Reject and recapture demos with unexplained page teleports, blank navigation flashes, clicks before the cursor arrives, abrupt scrolling, or important states that disappear before a viewer can understand them.
13. Revise and rerun when needed. To change styling only, edit `presentation.json` and run `node "$DR_CLI" render --project DIR --overwrite`; no recapture is needed. Report the raw recording path and the final rendered MP4 path separately, labeling the MP4 as the deliverable.

Follow [exploration safety](references/exploration.md) and [authentication handling](references/authentication.md). Do not import `references/` into production code. Never claim that Demo Recorder itself contains an LLM.
